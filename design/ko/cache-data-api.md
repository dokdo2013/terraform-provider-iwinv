# 캐시 데이터 API 계약 준비

[English](../en/cache-data-api.md) · [기능 범위](coverage.md)

C33 / T079는 **진행 중**입니다. 기존 `iwinv_content_cache` 리소스는 서비스 가입과 리퍼러를 관리합니다. 이미지·폴더·데이터 API 자격증명·토큰은 관리하지 않으며, 데이터 API 기능은 Provider에 등록하지 않았습니다.

## 실측한 접근 경로

2026-09-19에 이미 검증한 control-plane 계약으로 폐기용 `cache_lite` 서비스 1개를 생성했습니다. 생성 응답의 정확한 ID가 API에서 active, 콘솔에서 운영중 상태로 확인됐습니다. 콘솔의 관리페이지 링크는 `https://image001.share.cache.iwinv.kr/`로 연결됐고, 새로 만든 계정과 FTP 비밀번호로 컨텐츠 매니저에 로그인했습니다. API 키 관리 화면에는 기존 키가 없고 키 생성 버튼이 있었습니다. 이는 상품 하나의 관리페이지 연결 근거이며 모든 캐시 상품·호스트·계정의 이용 가능성을 검증한 것은 아닙니다.

키는 생성하지 않았습니다. 새 보안 접근 권한을 만드는 시점의 별도 승인을 요청했고 응답을 기다리고 있습니다. 문서의 인증·용량 경로에 인증정보 없이 GET을 각각 한 번 실행하자 모두 HTTP 400과 `api`, `apiCode`, 숫자 `code`, 문자열 `result`를 반환했습니다. 이는 미인증 요청의 거부 근거이며 인증된 응답 스키마나 API 성공 검증이 아닙니다.

이후 대장에 기록한 생성 ID로 테스트 서비스를 삭제했습니다. API 삭제 성공과 캐시 목록의 빈 결과를 확인했고, 검색 조건 없는 콘솔 목록을 새로 조회했을 때도 서비스 행이 없었습니다. 시작 전 목록도 비어 있었습니다. 이미지·폴더·데이터 API 키는 생성하지 않았습니다. 생성 자격증명·원응답·실제 ID는 Git 밖에 보관합니다. 이번 정리 성공으로 별도의 웹메일·OAuth 정리 실패 T056을 해소한 것으로 표시하지 않습니다.

## 문서 범위와 미확정 동작

[공식 규격서](https://help.iwinv.kr/manual/938)는 별도 API 키의 토큰 교환, 사용자 확인, 이미지·폴더 작업, 용량 조회를 설명합니다. 키 교환에는 Basic 인증, 다른 호출에는 token 필드를 안내합니다. 성공 응답 예시와 파라미터 표만으로 전송 인코딩이나 실제 필드 타입을 확정할 수 없습니다. 기능 대장의 `cache_data` 12개 항목은 모두 `implemented: false`, `live_verified: false`를 유지합니다.

## 구현 경계 제안

- 서비스 API의 자격증명·endpoint를 control-plane HMAC과 분리하고 서로의 키를 다른 서비스로 전송하지 않습니다. 관리페이지 로그인·FTP 비밀번호는 API 키가 아닙니다. 컨텐츠 배포 도메인으로 API origin을 추측하지 않습니다.
- 명시적으로 검증한 HTTPS origin에 서비스 클라이언트를 고정합니다. 다른 origin으로의 redirect를 거부하고 인증서 검증을 유지하며 Provider 설정·alias마다 클라이언트와 토큰을 분리합니다. 이번에 관측한 단일 호스트를 모든 계정의 기본값으로 일반화하지 않습니다.
- 교환한 토큰은 메모리에서만 유지하고 진단·리소스 속성·fixture에 기록하지 않습니다. 만료·갱신 계약을 검증한 뒤 갱신을 구현하며, 검증하지 않은 JWT의 내용을 권위 있는 사실로 사용하지 않습니다.
- 실측한 원격 식별자와 재조회 동작으로 이미지·폴더 소유권을 정합니다. 리소스 등록 전에 import, 이름 중복, 대소문자·경로 정규화, 이름 변경·이동, 덮어쓰기, 삭제, 부모 부재를 검증합니다. 생성 결과가 불확실할 때 이름이 같은 객체를 자동 채택하지 않습니다.
- HTTP 상태와 업무 결과를 함께 판정합니다. 크기·시간·요청 제한과 페이지 계약을 확인하고 결과 불명확한 업로드·이름 변경·이동·삭제를 반복하지 않습니다. 용량 단위와 정수 인코딩은 인증된 근거를 확보한 뒤 숫자 스키마로 정의합니다.
- Provider에서는 지원되는 서비스 API를 직접 사용합니다. 이번 콘솔 확인은 계약 조사이며 로그인·키 발급을 Provider 실행 경로로 넣지 않습니다. 이번 관측으로 문서화된 원격 키 관리 API가 확인된 것은 아닙니다.

## 다음 acceptance 검증

키 발급 승인 응답 이후 새 폐기용 서비스를 만들고 전용 키로 인증 조회와 계정 연결을 확인합니다. 요청 인코딩·응답과 오류 타입·토큰 만료를 기록한 뒤 소유한 폴더·이미지 하나씩의 생성·조회·수정·import·drift·삭제를 검증합니다. 다른 객체 보존, 부분 업로드, 잘못된 경로, timeout, 만료 토큰, 키 폐기 후 거부도 포함합니다. 키와 서비스를 삭제하고 콘솔·API 부재를 확인하며 공개 근거는 익명화합니다. 현재의 접근 경로와 미인증 거부만으로 T079를 합격 처리하지 않습니다.
