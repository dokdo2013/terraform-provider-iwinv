# 컨텐츠 캐시 수명주기 결정

[English](../en/cache-lifecycle.md) · [아키텍처](architecture.md) · 2026-09-19

타입이 있는 제어 API 어댑터로 캐시 상품·서비스 조회, 생성, 전체 리퍼러 교체, 삭제의 5개 작업을 구현했습니다.
T065는 신규 `cache_lite` 서비스 2개씩을 사용하는 두 차례 실행에서 통과했습니다. **Terraform 리소스는 아래 T066 근거로 등록했으며 상품 Data Source도 T067 근거로 등록했습니다.**

## 식별자와 관측 설정

`service_idx`는 부동소수점 변환 없이 정확한 양의 int64 십진 문자열로 유지합니다. Read는 전체 목록을 검증한 뒤 ID를 찾으며
잘못된/중복 행, 변경된 페이지·건수 메타데이터와 API 오류를 부재로 바꾸지 않습니다. 생성 ID는 나머지 응답 필드를 검증하기
전에 확보하고 부분 응답, 미검증 201/202와 후속 설정 실패에도 보존합니다.

Read는 상품 ID, 원문 별칭/설명, 계정 `id`, 상태, IP, 문자열 도메인, `spec.type`과 전체 리퍼러 목록을 제공합니다.
생성 응답은 상품 ID를 생략하므로 동일한 필수 필드 스키마로 디코딩하지 않습니다. 비밀번호, tenant API 키와 임의 응답 필드는
읽기 모델에서 제외합니다. 관측된 빈 리퍼러 배열은 누락/null과 구분합니다. DBMS와 달리 초기 계정명이 조회되므로
import에서 DNS를 보고 추측하지 않고 실제 계정을 복원할 수 있습니다.

C31: `cache_lite`의 카탈로그 등급은 `SHARE`인데 새 생성 응답 2개는 모두 `spec.type: SINGLE`입니다. 이전 실측과도 같습니다.
두 표기가 다르다는 이유로 정확한 상품을 거부하거나, 조회된 표기를 카탈로그 추정값으로 바꾸지 않습니다.
이 불일치 필드로 공유/단독 격리 수준을 보장할 수 없으며 상품 노출도 생성 자격을 보장하지 않습니다.
상품 목록에는 coming-soon이면서 `product_id`가 null인 행이 있으므로 null로 보존하고 생성 ID를 만들지 않습니다.
단위가 검증되지 않은 디스크·트래픽·가격 필드는 제외합니다.

## 비밀번호와 교체

공식 생성 스키마는 `ftppw`를 안내하지만 실환경 검증은 JSON `pw: {"FTP": "…"}`를 요구합니다.
어댑터는 확인된 중첩 입력만 보내고 초기 비밀번호를 대장 입력 모델에 직렬화하지 않습니다.
초기 비밀번호는 공백을 제외한 출력 가능한 ASCII 7–20자와 영문·숫자·기호 중 2종류 이상을 지원합니다.
계정 입력은 ASCII 영문·숫자 6–12자입니다. 한글 이름/설명 원문과 설명 생략의 실제 응답도 재확인했습니다.

등록된 `iwinv_content_cache`는 ephemeral `ftp_password_wo`를 state가 아닌 설정에서 읽으며,
새 초기 비밀번호를 의도적으로 적용할 양의 로컬 version 신호를 제공합니다. 신호 변경은 서비스 교체이며 비밀번호 회전 API는
확인되지 않았습니다. 이름·상품·설명·계정도 수정 API가 없으므로 교체합니다.
공급사는 복구 불가능한 삭제와 **삭제 후 계정명 24시간 재사용 제한**을 명시합니다. 따라서 일반 교체는 확정된 다른 계정과
새 초기 인증정보가 필요합니다. taint/`-replace`, import된 state, 생성 실패와 외부 삭제도 Core 테스트로 확인하며
같은 계정명으로 즉시 다시 만들 수 있다고 plan에서 약속하지 않습니다.

## 전체 리퍼러 집합 소유와 초기 설정

C22: 생성 시 `allow_referer`는 무시됩니다. 어댑터는 이 인자를 보내지 않으며 생성이 리퍼러를 적용했다고 주장하지 않습니다.
부모 리소스는 먼저 새 ID를 보존하고 서비스를 확인한 뒤 원하는 비어 있지 않은 집합을 별도 PUT으로 설정해야 합니다.
이 단계 사이 실패에도 과금되는 부모가 고아가 되지 않도록 식별자를 유지해야 합니다.

PUT은 JSON `allow_referer` 배열을 받아 전체 목록을 교체합니다. 부모 리소스 하나가 전체 집합을 소유해야 하며 개별 리퍼러
리소스는 충돌할 수 있습니다. 초기 지원 입력은 정규화된 소문자 ASCII DNS 호스트명입니다. wildcard, URL/경로/포트,
IDN과 IP 리터럴은 별도 계약 검증이 필요합니다. 미지원 기존 값을 조용히 정규화하거나 누락하면 안 됩니다.
빈 집합 초기화는 HTTP 422로 거부됐습니다. 최초 빈 설정은 PUT을 생략할 수 있지만 비어 있지 않은 집합을 비우려면
명시적 파괴적 교체나 별도로 검증된 초기화 API가 필요합니다. plan의 unknown 집합도 보수적 교체 처리가 필요합니다.

## 작업중 오류와 재시도

`active`만으로 쓰기 잠금 해제를 알 수 없습니다. 실측한 PUT/DELETE 거절은 HTTP 404, `code: 0x1`, `error_code: NOT_FOUND`와
다른 작업이 진행중임을 나타내는 동일한 message/result입니다. 이 조합이
`PUT /v1/cache/{정규화된-양의-int64}/allow_referer`에서 나오면 `cache_referrers_busy`,
`DELETE /v1/cache/{정규화된-양의-int64}`에서는 `cache_delete_busy`로 구분합니다. 서버 원문은 노출하지 않습니다.
다른 문자열·상태·메서드·서비스·잘못된 ID·일반 404·통신 실패·불확실한 결과는 일반 오류로 유지합니다.
분류 자체는 재시도하지 않으며 공통 클라이언트와 어댑터는 각각 한 번만 호출합니다.

T065는 첫 수정 접수 직후 다른 집합을 요청해 작업중 거절을 한 번 재현했습니다. 정확한 ID Read에서 부모가 존재하고
이전 목록 전체가 그대로임을 확인한 뒤 제한된 대기를 거쳐 동일 요청이 접수·조회됐습니다. 다른 서비스도 보존됐습니다.
이를 근거로 리소스 단계에서는 정확한 작업중 거절, 기존 집합 보존 Read, 작업 timeout 범위에 한정한 재시도를 설계할 수 있습니다.
행이 사라지거나 Read가 실패하거나 다른 작성자가 집합을 바꾸거나 응답이 달라지거나 기한이 만료되면 중단해야 합니다.
이미 접수된 쓰기나 결과가 불확실한 생성은 반복하지 않습니다.

두 번째 실행은 첫 실험의 삭제 전 45초 대기를 제거하고 수정 접수 직후 삭제했습니다. 첫 부모 삭제도 정확한 작업중 거절을
한 번 반환했으며 Read에서 소유한 부모의 전체 모델이 그대로임을 확인했습니다. 제한된 재시도는 삭제 접수와 부재 확인까지
성공했고 다른 서비스도 보존한 뒤 한 번에 삭제했습니다. 확인된 작업중 거절과 재조회가 있어야 다음 시도를 허용합니다.
통신 실패·다른 오류·이미 접수된 쓰기는 반복하지 않으며 고정 대기를 준비 상태의 보장으로 쓰지 않습니다.
이 근거는 어댑터 단계이며 아래 T066에서 Core의 실패 시 state와 복구 동작을 추가 검증했습니다.

## 근거와 남은 검증

`TestAccCacheControlPlaneWrites`는 Go race에서 첫 실행 89.81초, 두 번째 실행 45.49초로 통과했습니다. 신규 2개 공존, 중첩 비밀번호 생성, 원문/생략 설명,
전체 목록, 리퍼러 1개/2개 교체, 작업중 거절 1회와 기존 목록 보존, 다른 서비스 보존, 두 실행의 서비스 ID 총 4개의 삭제 응답·정확한 부재를 검증했습니다.
두 번째 실행은 인위적 삭제 전 대기 없이 삭제 작업중 거절과 부모 보존도 검증했습니다. 첫 실행 후 콘솔의 검색 필터 없는 캐시 목록은
비어 있었으며 두 번째 실행의 API 삭제 응답·부재 근거도 별도로 기록했습니다. 비공개 대장에는 의도·생성 ID·쓰기 시도/접수·정리 관측을 남기고
공개 fixture는 합성 값만 사용합니다. 합성 테스트는 2^53 초과 ID, null 상품, 잘못된/부분 응답, 자격증명 제외,
미지원 입력과 자동 재시도 없는 좁은 작업중 분류를 검증합니다. 기존 인프라는 변경하지 않았습니다.

남은 범위는 다른 상품, wildcard/빈 집합 제자리 초기화, tenant API 인증, 컨텐츠/FTP 접속, purge와 과금입니다.
원래 목표에 계속 포함합니다. 어댑터 통과로 전체 T037/T038/T039나 정리 T056을 완료 처리하지 않으며 웹메일은 별도입니다.

## 등록된 Core 리소스 (T066)

`TestAccContentCache`는 Terraform 1.14.2와 Go race에서 116.04초로 통과했습니다. 새 ID 5개로 두 서비스 공존,
처음부터 빈/비어 있지 않은 리퍼러, ID를 유지하는 전체 목록 수정, 외부 drift 복원, 전체 조회 필드 import,
비밀번호·버전 없는 재import와 무변경 plan, 새 계정의 빈 집합 create-before-destroy, 비밀번호 버전·설명 교체,
외부 삭제 후 새 계정 재생성을 검증했습니다. PUT 작업중 거절 한 번을 재조회 후 처리했습니다. 이번 실행에는 DELETE 작업중
거절이 없었으므로 해당 분기는 별도 T065 실환경 계약과 합성 Core로 검증합니다. 5개 모두 삭제 접수와 정확한 ID 부재를 확인했고,
독립적으로 새로고침한 콘솔에서도 검색 조건 없이 서비스 행이 없었습니다. 기존 인프라는 변경하지 않았습니다.

저장된 압축 plan과 state에서 생성한 ephemeral 비밀번호의 비저장을 검사했습니다. 전체 import 비교는 복원 불가능한 로컬
비밀번호 버전만 제외합니다. 합성 Core는 설정 실패 후 ID 정리, 잘못된 생성 응답, 조회 지연, taint·명시적 교체 plan,
unknown 전체 집합의 교체, 순서, 누락·미지원 입력, timeout·오류 시 state 유지, 부모 변경·부재·조회 실패 시 작업중 재시도
중단도 검증합니다. 접수되거나 결과가 불확실한 쓰기는 반복하지 않습니다.

리퍼러 기본값은 빈 집합이고 기존 비어 있지 않은 집합을 비우면 교체합니다. 일반 교체는 확정된 다른 계정명과 초기 비밀번호가
필요합니다. timeout 기본값은 쓰기 5m·읽기 1m입니다. [리소스 가이드](../../docs/ko/resources/content_cache.md)에 import·비밀번호·복구를 설명합니다.
전체 T038과 별도로 미해결인 웹메일 정리 T056은 완료 처리하지 않습니다.
