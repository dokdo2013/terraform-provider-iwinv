# 로드맵과 작업 단위

[English](../en/roadmap.md) · [목차](../../README.md) · 리비전: 2

초기 커밋은 Provider 구현 완료를 의미하지 않습니다. 단계별 검증을 통과하며 진행하고,
첫 릴리스가 작더라도 최종 목표는 API·CLI가 제공하는 전체 원격 리소스 지원입니다.

| 작업 | 선행 조건 | 산출물 | 완료 조건 |
| --- | --- | --- | --- |
| P0 설계 기반 | 없음 | 공개 레포, 양언어 설계, 기능 대장, 체크리스트, 문서 CI | 로컬/원격 검사 성공, 한계 명시 |
| P1 API 계약 검증 | P0 | 마스킹 조회 fixture, 인증/인코딩/페이지/오류 계약, 나머지 기능 조사, 버전 ADR | G1 통과, 공백별 근거와 담당 |
| P2 Compute 최소 수직 구현 | P1 | Go client, Framework Provider, 카탈로그 조회, 서버 수명주기/import | G2·G3 통과, 무변경 plan, 서명 prerelease 후보 |
| P3 네트워크·스토리지 | P2와 C14–C17 해소 | 그룹/규칙/연결, 연결 소유자가 하나인 스토리지 수명주기 | 리소스별 G4, import·의존성 삭제 검증 |
| P4 기타 control-plane | P1과 서비스별 계약 해소 | 호스팅/캐시/DBMS/NAS/웹메일, 상품, 허용 목록, 청구, 키/스크립트 조회 | 기능별 C19–C23 해소, 비밀번호·파괴적 교체 문서화 |

| P6 안정 릴리스·사용자 교육 | P2–P5 증거 | 버전/state migration, Registry 배포, 완성된 한·영 가이드 | G5 통과, 정확한 출시 범위; 전체 대조 후에만 전체 지원 선언 |

P2 이후 제한된 범위의 prerelease는 가능합니다. 일부 지원을 전체 지원으로 소개하지 않으며,
모든 서비스 완성 전에도 사용자 피드백을 받습니다. 일정은 API 접근성과 공급사 답변에 따라 결정합니다.

## 남은 작업의 실행 순서 (2026-09-23 기준)

현재 개발 Provider는 Data Source 18개와 리소스 7개를 등록합니다. 등록된 기능의 세부 실환경 범위는
[구현 대장](../inventory/implementation.json), 검증 상태는 [체크리스트](../inventory/checks.json)를 따릅니다.
**80개 검증 중 통과 27개, 진행 23개, 미실행 28개, 실패 2개**입니다. 이 수치는 기능 지원률이 아닙니다.
API 키에 현재 테스트 출발 IPv4를 허용한 뒤 인증된 읽기 요청이 다시 HTTP 200/SUCCESS를 반환했습니다.
테스트 웹메일 서비스는 인증된 콘솔의 삭제 이력과 빈 서비스 목록으로 정리를 확인했습니다.
반면 기존 MCP OAuth 임시 등록의 삭제, Compute 생성 가능 존과 서버 수명주기, Registry 출시는 미확인입니다.
웹메일 한 건의 정리로 전체 정리 검증 T056을 합격 처리하지 않습니다. 실제 계정 ID·IP·응답·비밀값은 공개 문서에 넣지 않습니다.

| 순서 | 지금 수행할 일 | 다음 단계 진입에 필요한 증거 |
| --- | --- | --- |
| **#1 / P1** | 복구된 API 접근으로 서명·페이지·오류·필드 마스크의 잔여 T001–T010을 대조합니다. 공급사에 현재 계정의 Compute API 존·상품·기존 서버 가시성, 생성 제한 오류, 등록된 MCP 클라이언트 정리 경로와 필요한 서비스별 인증을 문의합니다. 인증된 MCP 도구 목록은 등록 정리와 OAuth 범위를 해결한 뒤에만 조사합니다. | 존/상품 이용 조건과 안전한 수명주기 fixture가 확인되고, G1의 합격·미합격 범위가 근거와 함께 기록됩니다. T014는 CLI·서비스 API·MCP 공백까지 대조한 뒤 판정합니다. |
| **#2 / P2** | 이미 작성한 Compute 읽기·쓰기 어댑터를 실제 계정 계약과 대조합니다. 소유한 서버 한 대의 생성 ID, 완료 대기, Read·수정·import·drift·삭제를 검증한 다음 `iwinv_instance`를 등록합니다. 결과 불명확 생성은 자동 재전송하거나 이름으로 채택하지 않습니다. | T015 실패 원인을 해결하고 T016–T030과 G2·G3을 실환경/합성 구분으로 통과합니다. 생성한 모든 ID의 정리와 잔여 디스크·과금 판정을 남깁니다. |
| **#3 / P3** | 기존 보안 그룹·규칙 지원을 유지하면서 서버 연결의 추가/교체 의미를 실측합니다. 블록 스토리지의 생성 시 서버 의존성, 분리·재연결·삭제·보존을 검증해 단일 연결 소유자를 정합니다. | T031–T036과 기능별 G4에서 import·drift·의존성 삭제가 통과합니다. 서버를 만들 수 없으면 연결·볼륨 지원을 완료로 표시하지 않습니다. |
| **#4 / P4** | 기존 호스팅·DBMS·캐시·NAS 지원의 상품별 미검증 수명주기를 채웁니다. 웹메일 서비스의 Read/삭제 일관성과 계정 목록/상세 대체 경로를 확인하고, 청구 상세 권한·시간대 공백을 다룹니다. | 각 기능의 C19–C23, T037–T042와 G4가 충족됩니다. 메일 계정의 신뢰할 만한 Read가 없으면 관리 리소스로 출시하지 않습니다. |
| **#5 / P5** | 오브젝트 스토리지, NAS/캐시 데이터 API, 메시징·템플릿, 명시적 Action과 만료 값용 Ephemeral을 서비스별 자격증명·오류·소유권 계약에 맞춰 구현합니다. 검증된 MCP 도구를 API/CLI 기능 대장과 대조합니다. | T043–T050 및 캐시 T079를 기능별로 통과하고 모든 원격 기능에 구현 또는 확인된 공급사 제약을 연결합니다. 발송·데이터 이동은 합의된 테스트 범위에서만 실행합니다. |
| **#6 / P6** | 확정된 출시 범위의 한·영 문서와 예제를 점검하고 운영 서명키·Registry 공개키·제한된 게시 workflow를 준비합니다. 불변 버전을 서명·게시한 뒤 새 환경에서 Registry 설치와 실제 plan을 확인합니다. 이후 릴리스가 생기면 이전 state의 migration을 검증합니다. | T051–T056과 G5를 근거로 판정합니다. OAuth 등록을 포함해 이번 작업의 자원 정리가 확인돼야 T056을 다시 평가합니다. 첫 릴리스에는 이전 공개 버전이 없으므로 T054를 거짓 합격으로 바꾸지 않습니다. |

가장 가까운 실행 묶음은 **#1의 존/상품 이용 조건과 MCP 등록 정리 문의 → API 계약 재검증 →
#2의 폐기 가능한 서버 한 대 수명주기 검증**입니다. 공급사 답변 전에도 합성 테스트·릴리스 설계는 준비할 수 있으나
실환경 근거를 대신하지 않습니다. P2와 정리 조건을 통과한 제한된 prerelease는 전체 서비스 완료 전에 별도로 낼 수 있습니다.
최종 목표인 API·CLI의 모든 원격 기능과 한국어·영어 안내는 #1–#6 전체에 유지합니다.

## 이슈 준비

각 작업은 계약 Cxx와 검증 Txxx를 연결하는 추적 이슈로 만듭니다.
구현 이슈에는 범위·의존성·API 근거·예상 plan·import ID·양언어 문서·복구·테스트 정리를 포함합니다.
[기능 이슈 템플릿](../../.github/ISSUE_TEMPLATE/capability.md)을 사용합니다.
초기 GitHub 이슈는 이 작업 문서를 연결하며 설계의 기준은 저장소 문서입니다.

## 결정 기록

ADR에는 배경·대안·선택·영향·근거·테스트를 기록합니다.
미확정 사항은 최소 도구 버전, 수정/교체 정책, 연결된 볼륨 소유권, 읽을 수 없는 생성 입력,
집합 허용 목록, Action 이후 state 정합성, 서비스별 인증 스키마입니다.
scaffolding을 진행하려고 알 수 없는 API 동작을 임의 확정하지 않습니다.
